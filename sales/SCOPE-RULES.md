# 외주 범위 / 가격 방어 규칙

이 문서는 저가 수주 후 무제한 기능 추가로 수익성이 무너지는 상황을 막기 위한 **견적 기준**입니다. 실제 계약/플랫폼 정책에 맞게 조정해서 사용합니다.

---

# 1. 가격은 페이지 수보다 업무 복잡도로 산정

아래 요소가 늘어날수록 가격도 올라갑니다.

- 사용자 역할 / 권한 수
- DB 테이블과 관계
- 업무 상태 전이
- 외부 API 수
- Excel/CSV 양식 수
- 기존 코드 수정 범위
- 데이터 migration 규모
- 배포 환경 수
- 테스트/문서 요구 수준
- 실시간 처리 / 대량 처리

단순 화면 10개보다 복잡한 승인 흐름 1개가 더 비쌀 수 있습니다.

---

# 2. 기본 시작가

| 유형 | 시작가 | 기준 |
| --- | ---: | --- |
| 작은 기능 / 단일 자동화 | 49만원 | 범위가 명확하고 독립적인 기능 |
| 관리자 기능 / 업무자동화 | 149만원 | CRUD + 검증 + 업무 흐름 |
| 풀스택 업무시스템 | 299만원 | UI + API + DB + 상태/권한 |

이 가격은 **무제한 포함 가격이 아니라 최소 구현 단위의 시작점**입니다.

---

# 3. 견적에는 반드시 포함/제외를 같이 작성

## 포함 예시

- 거래처 CRUD
- 검색/상태 필터
- 업무 접수
- RECEIVED → IN_PROGRESS → DONE 상태 전이
- 관리자 계정 1종
- Excel export

## 제외 예시

- 결제
- 문자 발송
- 고객용 모바일 앱
- ERP 연동
- 기존 데이터 전체 migration
- 서버 비용

제외 항목을 적지 않은 견적은 추후 분쟁 가능성이 높습니다.

---

# 4. 완료 조건을 사용자 행동으로 작성

나쁜 예:

> 관리자 기능 개발 완료

좋은 예:

> 관리자가 고객을 검색·등록·수정할 수 있고, 해당 고객의 업무를 접수한 뒤 접수 → 진행 → 완료 상태를 변경할 수 있다.

기능 이름보다 **누가 무엇을 해서 어떤 결과를 확인할 수 있는지**로 완료 조건을 적습니다.

---

# 5. 수정과 기능추가를 분리

## 수정

합의된 요구사항대로 구현했지만 표시/동작이 맞지 않는 부분을 조정하는 것.

## 기능추가

처음 합의하지 않은 입력, 화면, 상태, 권한, API, 데이터 관계를 새로 넣는 것.

기능추가는 수정 횟수에 포함시키지 않고 **추가 견적 또는 다음 단계**로 분리합니다.

---

# 6. 초기 상담에서 위험 신호

다음 요청은 범위를 더 명확히 한 뒤 견적합니다.

- “간단한 사이트입니다”라고 하지만 기능 목록이 없음
- “일단 만들어보고 추가하자”
- 기존 소스가 있는데 저장소/실행방법을 모름
- 외부 API 문서가 없음
- 여러 사용자 역할이 있는데 권한 기준이 없음
- 기존 Excel 양식이 업체별로 다르지만 샘플이 없음
- 정확한 완료 조건 없이 특정 날짜만 고정
- 예산은 매우 낮지만 ERP/플랫폼 전체를 요청

거절보다 **1차 핵심 기능으로 범위를 축소**하는 제안을 먼저 합니다.

---

# 7. 단계별 개발 권장

복잡한 프로젝트는 다음처럼 나눕니다.

```text
Phase 1 · Core
CRUD / 핵심 입력 / 상태 처리

Phase 2 · Operations
권한 / Audit / Excel / Dashboard

Phase 3 · Integration
외부 API / 자동화 / 배포 고도화
```

각 Phase는 독립적으로 검수 가능한 완료 조건을 가져야 합니다.

---

# 8. 기존 시스템 수정은 사전 분석을 범위에 포함

기존 프로젝트는 신규 개발보다 변수가 많습니다.

확인 항목:

- 로컬 실행 가능 여부
- 빌드 성공 여부
- DB schema
- 환경변수/secret
- 테스트 유무
- 배포 방법
- 변경 대상 코드 의존성

분석 없이 고정가부터 제시하지 않습니다.

---

# 9. 외부 비용은 개발비와 분리

개발비와 아래 비용은 별도로 안내합니다.

- 서버 / DB
- 도메인
- 문자 / 이메일
- 결제 수수료
- 지도 / AI / 데이터 API
- 스토리지
- 앱스토어 계정

외부 서비스 정책이나 가격 변동까지 개발자가 무기한 책임지는 구조를 만들지 않습니다.

---

# 10. 유지보수는 범위를 다시 정의

납품 후 유지보수는 다음을 분리해서 협의합니다.

- 납품 범위 내 결함 수정
- 운영 중 정책 변경
- 신규 기능
- 외부 API 변경 대응
- 서버 장애 대응
- 정기 모니터링

“유지보수 포함” 한 줄로 무제한 지원을 약속하지 않습니다.

---

# 11. 플랫폼에서 첫 가격을 낮출 때도 범위를 낮춘다

초기 리뷰 확보를 위해 가격을 낮추더라도 **원래 큰 범위를 싸게 제공하지 않습니다.**

예:

```text
49만원
→ 고객/업무 전체 시스템 X
→ 기존 페이지의 명확한 기능 1개 O
```

가격을 내리면 기능 범위도 같이 줄입니다.

---

# 12. 최종 견적 체크리스트

견적 발송 전 확인:

- [ ] 사용자 종류가 정해졌는가
- [ ] 필수 기능이 정해졌는가
- [ ] 상태 흐름이 정해졌는가
- [ ] 입력/출력 데이터가 정해졌는가
- [ ] 외부 API가 확인됐는가
- [ ] 기존 코드 유무를 확인했는가
- [ ] 포함 범위를 적었는가
- [ ] 제외 범위를 적었는가
- [ ] 완료 조건을 적었는가
- [ ] 외부 비용을 분리했는가
- [ ] 기능 추가 처리 방식을 정했는가
